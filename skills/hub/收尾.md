# 收尾

大总管派出的会话，在上线或交付后的那一轮读这份照做（2026-11-12 Samuel 定）。下面三条各有条件，有才做，没有就不写；拿不准就不加。登记了什么，在收尾汇报里写给用户。

`H` 表示 `python3 /Users/qiansenmiao/tasks/hub/bin/hub.py`。会话 ID 自动取本会话的，不用填；每个命令加 `--help` 看各项填什么。

## 1. 回看效果

**什么时候要**：改动是为了让人的做法或某个数变化，而且上线当时看不出效果。例：提醒卡、建联规则、打开追踪留对照组、统计口径。Bug 修复上线当时验证完的不要；私事、调研不要。

**登记两项，各跑一次 `H review add`**：

- **跑没跑对**：新逻辑有没有按预期跑。时间由事件多久发生一次定：高频的（例：建联规则每发一封首封就触发，11-10 一天 915 封首封、342 封命中）上线后 1 小时就能看；低频的（例：每天两轮的提醒卡）按它第一次真实触发的那一轮看，不按上线后几小时看。上线后马上看错误日志已有规则，不用登记。
- **有没有用**：要的效果有没有出来，`--value` 必须写现在是多少（上线前同样时段的数），到期时拿它比。时间由效果多久显现定：人当场就会做的反应（看到提示后改没改、发没发）上线当天能看；要等别人回应的（达人回不回、组员提不提报）要等指标窗口走完（24 到 72 小时），和上线前同样的工作日比；要的效果是回复率这类结果的，用第一个完整周。月会用整月。
- **例外**：会对外发信、发出去收不回的改动（例：建联规则从只提醒改成拦截、批量发信），第一批真实发送后在本会话马上看，第一个小时内再看一次：再看的那次登记成一条「跑没跑对」。
- 收尾这一轮已经在本会话看过的那一项不登，在收尾汇报里写看到了什么。

```bash
H review add --check 跑没跑对 --metric "命中数、报错数、提示内容对不对" --on "2026-11-12 15:00" --why "一天 900 多封首封，1 小时样本够"
H review add --check 有没有用 --metric "提醒后 24 小时提报率" --value "8%（11-05 至 11-11）" --on 2026-11-19 --why "要等 11-12 到 11-18 一整周"
```

`--on` 只写日期的，当天 11:00 汇总列出来；写到分钟的，到点后用户下一次和大总管说话时提一次。到期没看的，每天 11:00 汇总都列，直到看完。

**到期以后**：用户回到本会话说「回看」。重新算这个数，然后运行 `H review done --result "11-19：35%"`（本会话只有一条到期时不用写 `--id`；有几条时先 `H review list` 查编号）。还要再看的，再 `review add` 一条新日期。用户说不看了：`H review done --cancel`（没到期的那一条先 `H review list` 查编号，加 `--id`）。

所有回看都做完之前，本会话不进大总管汇报的「做完了」，也不算在制。

## 2. 顺带发现的事

做这件事时发现、但不属于这件事的问题。有才写，每条一句，写清是什么、影响谁，不用写怎么改。登记后出现在大总管汇报的「新收集到的」里，由用户决定开不开会话。

```bash
H found --text "离职同事名下 13 个邮箱没交接，29 封来信没人处理" --text "提醒发出后 92% 没提报"
```

## 3. 想法从哪来（试行到 2026-11-25，之后命令不再记）

这件事里比派单更上一层的问题（改变了要做什么、或怎么判断成没成）是谁、在哪一步提出的。有才写。

```bash
H idea --question "提醒后半天只有 8% 去提报" --by 会话算出来的 --step "第 2 步排查"
```

`--by` 只能是：用户问的、会话算出来的、数据看出来的。
