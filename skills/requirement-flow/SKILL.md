# 新需求流程

用户的做法：直接描述需求，让 AI 出方案，一起沟通方案，定了就开工。下面四步是 2026-11-05 和用户逐条定下的。

## 总规则

- 沿用 `investigate-flow` 的总规则：一条一条过，不让用户读长文件；一个会话只做一件事；被 hook 拦下的处理。
- 本流程固定的 5 个确认点，到了就停下等用户：
  1. 需求清单和空白的推荐值（第 1 步结束）；
  2. 方案里的每个决定点（第 2 步）；
  3. 任务单「开工」（第 3 步结束）；
  4. 「上线」（验收后）；
  5. 通知需求方之前的「发送」。

  另外两种情况也要问：任务单没授权的操作、超出任务单范围的情况（同 `investigate-flow`）。
- 要用户决定的消息，开头写「需要你决定：」加一句话，再写选项和各自代价，最后写不决定会怎样。
- 估时：派子 agent 写的预计，按实测打折（直觉估的时间，实现除以 4、调研除以 3、审查除以 2.5）；给用户报时间分两段：「AI 写完、开出 PR 约 X」和「到上线约 Y」（Y 含审查、CI、测试环境验收、等用户验收）。见 AGENTS.md「派单按工作量估时」。
- 同一个需求上线后口径或范围变了，或者要做二期，从第 1 步重走：先更新需求清单，再出方案。

## 第 1 步：收集需求

- 读全所有来源：需求文档、会议记录或纪要、用户和需求方的私聊（`lark-im`，lark-cli 带 `--profile ordo`）、截图、相关的飞书评论，不经过幕僚。读不到的请用户贴原文，并在清单里标「未读到」；只有截图、找不到原话出处的，也标出来，确认时一起问。
- 交出需求清单，每条写：原话、出处（文档位置；会议原话带时间戳）、需求方是谁。
- 会上或业务方已经定的规则，照原意记。你有不同意见，另列「提议」，不改默认实现。
- 列出空白：原文没说、但做的时候必须定的地方，例如次数、口径、计数单位（封、会话、人）和分母、起算点、范围边界、谁能看到。每个空白填推荐值，配一个具体例子，标明「原文没写，这是我的推荐」。
- 停下：需求清单和空白的推荐值一起给用户，一次确认。
- 需求方表示自己还要再理一下的，停在这一步，等对方定稿后重读来源。
- 用户拍板的就算定。规则会改变业务同事日常操作的，提醒用户一句：要不要找业务负责人确认，由用户决定，你不自己卡住等。

## 第 2 步：出方案

- 方案第一段讲业务含义：做完以后谁能做什么、能看到什么。不用内部术语，不造新词。用户听懂了，再讲怎么实现。
- 方案分两块：
  - **第一版**：最快能上线验证的版本；
  - **打磨清单**：上线后再定。

  守卫、权限默认拒绝、接口冻结这类防御放进打磨清单，除非需求原文要求，或者会写入、删除生产数据。会改变业务同事日常操作的规则，可以把「带 env 开关（off / warn / block），回滚只改开关」作为提议写进方案。
- 每个决定点最多 3 个选项，写推荐、代价和具体例子。计算口径配例子讲，例如两种起算方式用一张日期表对比；口径的例子尽量用生产只读查询算出的真实数字。数字要实测（生产只读查询、实际耗时），没测的标 [推断]。
- 用户给过方向的，按用户的方向出方案，包括以问句给的方向（「用 sorted set 能不能少扫库？」）。用户说「你来评估」的，按用户倾向的方向出方案，另附一条实测的评估结论。你有异议，拿实测证据另列提议，不自己换方向。
- 方案全文写文件作底档，在对话里一条一条讲。

### 大需求：交给用户前过 Codex 复核

大需求指满足任一条：改表结构或新增表；涉及两个以上服务或仓库；会改变业务同事日常操作的规则。不按预计时长判断。

1. 把需求清单（含已确认的空白）和方案写进一个文件。
2. 用 `investigate-flow`「独立复核」里的 `codex exec` 命令，prompt 换成：

   ```text
   读 $CLAIMS（需求清单和方案）。只查两件事：1）需求清单里有、方案漏掉或改了意思的；2）方案里有、需求没要求的东西（功能、防御、抽象）。每条写位置和理由。不要提出新的需求或新的防御。用中文回答。
   ```

3. 读结果：漏掉或改了意思的，改方案；需求没要求的，删掉或放进打磨清单；Codex 提出要加的防御，一律放进打磨清单；要改动用户已确认的需求的，交给用户决定。
4. 失败处理同 `investigate-flow`：重试一次，再失败改用子 agent，两条路都失败就标「未复核」报给用户。

## 第 3 步：定任务单

方案已经在第 2 步逐个决定点确认过，第 3 步不重新选方案，只把定下的方案写成任务单。任务单用 `investigate-flow` 的模板，改两项：

- **第 1 项**「根因和改法」改成「需求和方案」：第一版做到哪里，哪些放进打磨清单。进度表里这一项也用这个名字。
- **第 6 项**「回复报问题的人」改成「通知需求方」：发给谁，走什么渠道，请对方确认什么。

另外：

- **第 2 项完成标准**另外要求：
  - AI 自己造测试数据，自己跑端到端，不等用户提供数据；
  - 页面在浏览器里看过，包括小屏（例如 14 寸 Windows 常见的 1366×768 视口），列放不下时要能横向滚动或折叠；
  - 按时间计算的规则留一个能改时间的测试入口，例如用配置项把「24 小时」阈值缩到 5 分钟。
- **第 4 项上线范围**写明发布顺序（表结构变更、后端、前端的先后），以及旧代码能不能兼容新表结构。

每项附一句「为什么」，在对话里逐项过给用户，用户说「开工」才动手。

## 第 4 步：执行、验收、上线

照 `investigate-flow` 第 4 步的「执行」「验收」「上线」做。「收尾」的第一条换成：

- 上线后拿第一批真实数字，按任务单第 6 项起草给需求方的消息，请对方确认口径。给用户看，用户说「发送」再发。

释放测试环境、移出「待验收」两条照旧。

## 依据

- 09 达人库治理：方案是满篇术语的文件，用户说「说人话」；开工 7 天后才砍掉不该做的搜索和候选查询；守卫、默认拒绝等防御和「先跑通」反复冲突，开工到首次上生产约 11 天。
- 10-27 博主联系规则：AI 改了会上定的「停发 60 天」，自定口径「回了就算」；用户拍板后仍放进提议等 Leon 确认；验收时用户要求 AI 自己造数据、自己 E2E。
- 10-26 博主来信未回复提醒：需求只有截图，AI 补了「每天汇总一次」；需求方天振不在会话里，上线后口径改了 3 次；上线前只跑了单测和 CI，页面没在浏览器里看过；用户给的 Redis 方向被换成 MySQL 小表。
