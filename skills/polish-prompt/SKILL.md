# 完善 prompt

Samuel 11-24 的原话：「有时候我是想帮我完善优化一个prompt，因为我感觉我说不明白」。输入是他的一句话，加上当前对话里他正在看的内容。输出是一份 prompt。一轮给出，不先提问，不出方案，不动手做。

## 做法

1. **找他要的结果。** 他的话常常是一个动作（「开吧」「查一下」「把 X 修了」）。问一次「这件事做完，他要的是什么」，把答案写成 prompt 的第一句。他的话只有「开吧」「做吧」这类时，那句话指的是对话里上一段讲的事，从那一段里找。
2. **看有没有第二种理解。** 判据：换一种理解，接单的会话要做的事不一样。有的话，prompt 按最可能的一种写，其余的各用一行列在 prompt 下面给他挑，最多 3 种，从小到大排：
   - 只做眼前这一件；
   - 把眼前这个指标或现象解决掉；
   - 他负责的这个系统里，这一类结果以后不再出现。「这一类」按他看得到的现象分（慢查询、出了错没人知道、信丢了），范围写到整个系统（邮件系统、Brand 平台），不按这一次的原因分（「别的轮询有没有同样的写法」太窄）。这种理解要包含两半：现有的找全修掉，新出现的有办法先发现或拦住。

   起因是一次故障、一个同事的反馈、一张截图时，第三种一定要列出来：他常常要的是这一种，但嘴上只说了眼前这一件。
3. **补他没说、但接单的会话必须知道的。** 只补三样：怎么算做到；范围，以及明确不做什么；已知的材料和出处（链接、会话、文件），并写「开工先核对」。对话和文件里读得到的才补，读不到的写成「没说：…，开工先问他」，不编。时间、数字、人名照对话里的原样写（「昨晚 20:59」不换算成日期）。
4. **不加他没要的。** 不加方案、步骤、防御、估时、流程说明。用他的词，不换成术语。

## 输出

````
```
<要的结果，一句话>
怎么算做到：<…>
范围：<做什么>；不做：<…>
已知：<材料和出处>，开工先核对。
没说：<…>，开工先问他。
```
我补的：① <…> ② <…>
别的理解：B <一行> ／ C <一行>
````

- 代码块里是给接单会话的 prompt，哪一行没有内容就不写。能写短就写短，通常 3–6 行。
- 「我补的」逐条列出他原话里没有、你加进去的内容，编号。他回「去掉 ②」就删那一条，回「B」就按那种理解重写。
- 只有一种理解时不写「别的理解」一行。
- 代码块之外不再写别的话。

## 原话已经清楚时

判据：做什么、对谁做、做到哪里都在话里（例：「把现在试点的邮件分类给所有人都打开」）。这时回一行「已经清楚，可以直接用」，把原话原样放进代码块，不改写，不加长，不列「别的理解」。

接单的会话自己查得到的事（开关在哪、代码在哪、现在是什么状态）不算没说清，不为它改写。要不要先评估、要不要谁确认，是流程的事，不算第二种理解。

## 例子

对话里上一段讲的是：Joe 说数据库压力有点大，Core 主库 IOPS 98%，读压力头号来源是邮件发信收尾轮询，第三是今日发送数统计。他说：「开吧，下一条」。

````
```
邮件系统对 Core 主库的读压力降下来：先修发信收尾轮询反复读已完成记录、今日发送数统计缺索引这两处，再把邮件侧其他慢查询找全列给他。
怎么算做到：上线前后对比这两个查询的单次耗时和读行数，主库 IOPS 使用率回落。
范围：邮件侧的查询；不做：别的模块的查询、扩容，只量出占比。
已知：Joe 11-17 20:59 研发部群的两张截图，开工先核对现在还是不是这样。
```
我补的：① 把其他慢查询找全 ② 上线前后对比 ③ 别的模块只量不改
别的理解：A 只修截图里这两处 ／ C 邮件系统所有 SQL 以后都不出现慢查询、复杂查询、长 SQL：除了修现有的，还要有办法拦住新写的
````

他当时要的是 C。只给他一个理解、夹在一长段里，他没有异议就过了，做完才发现不是他要的。所以别的理解每种一行，单独列出来。

## 和别的 skill 的关系

- `raise-target`：大总管开会话前写完整派单用，照旧。他点名要「优化 prompt」时用本 skill。
- 本 skill 只管把话写清楚。写完他说「派」，再按 `hub` 的开会话步骤走。
