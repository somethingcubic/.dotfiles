# 完善 prompt

Samuel 11-24 的原话：「有时候我是想帮我完善优化一个prompt，因为我感觉我说不明白」。输入是他的一句话，加上当前对话里他正在看的内容。输出是一份 prompt。一轮给出，不先提问，不出方案，不动手做。

## 做法

1. **找他要的结果。** 他的话常常是一个动作（「开吧」「查一下」「把 X 修了」）。问一次「这件事做完，他要的是什么」，把答案写成 prompt 的第一句。他的话只有「开吧」「做吧」这类时，那句话指的是对话里上一段讲的事，从那一段里找。
2. **起因是一件具体的事时，默认写成「先修这一件，同时查这一类」。** 起因是一次故障、一个同事的反馈、一张截图时，他通常把它看成整个系统里被发现的其中一处（11-24 他定）。prompt 按两半写：
   - 先快速修好眼前这一件；
   - 同时在他负责的整个系统里排查同类问题，找全列给他。「同类」按他看得到的现象分（给数据库加了不该有的压力、出了错没人知道、信丢了），范围写这件事出在的那一个系统的全部（事出在邮件系统，就写整个邮件系统，不带上别的系统），原因不设限（SQL、索引、表结构都算），不按这一次的原因分（「别的轮询有没有同样的写法」太窄）。

   起因不是一件具体的事（他直接给了一个目标、一个调研问题、一个明确的改动）时，不套这一条，按他的话写。
3. **有别的理解就列出来。** 判据：换一种理解，接单的会话要做的事不一样。各用一行列在 prompt 下面给他挑，最多 2 种。第 2 条的情况固定列这两种：A 只修眼前这一件；C 再加一层，以后新出现的同类问题能先发现或拦住。
4. **补他没说、但接单的会话必须知道的。** 只补三样：怎么算做到；范围，以及明确不做什么（「不做」只写不碰的对象，生产只读这类做事的规矩不写）；已知的材料和出处（链接、会话、文件），并写「开工先核对」。对话和文件里读得到的事实才补，不编。
   - **做到什么程度算合格，由我们定，不问他。** 他只是把问题抛出来，标准是解决问题的人该给的（11-24 他定）。「怎么算做到」按这类问题业内公认的做法写成具体标准（例：线上高频查询走索引、不全表扫描，扫描行数和返回行数同一量级，轮询类查询单次在毫秒级）。你拿不准具体数的，写「达标线由接单的会话按业内做法定，写明依据」，不写「开工先问他」。
   - **只有他才知道的事才留给他**：给谁看、哪天要、业务上选哪一种、动不动别人的模块。这类写成「没说：…，开工先问他」。时间、数字、人名照对话里的原样写（「昨晚 20:59」不换算成日期）。
5. **不加他没要的。** 不加方案、步骤、防御、估时、流程说明。用他的词，不换成术语。

## 输出

````
```
<要的结果，一句话>
怎么算做到：<…>
范围：<做什么>；不做：<…>
已知：<材料和出处>，开工先核对。
没说：<…>，开工先问他。
```
我补的：① <…> ② <…>
别的理解：A <一行> ／ C <一行>
````

- 代码块里是给接单会话的 prompt，哪一行没有内容就不写。能写短就写短，通常 3–6 行。
- 「我补的」逐条列出他原话里没有、你加进去的内容，编号。他回「去掉 ②」就删那一条，回「B」就按那种理解重写。
- 只有一种理解时不写「别的理解」一行。
- 代码块之外不再写别的话。

## 原话已经清楚时

判据：做什么、对谁做、做到哪里都在话里（例：「把现在试点的邮件分类给所有人都打开」）。这时回一行「已经清楚，可以直接用」，把原话原样放进代码块，不改写，不加长，不列「别的理解」。

接单的会话自己查得到的事（开关在哪、代码在哪、现在是什么状态）不算没说清，不为它改写。要不要先评估、要不要谁确认，是流程的事，不算第二种理解。

## 例子

对话里上一段讲的是：Joe 说数据库压力有点大，Core 主库 IOPS 98%，读压力头号来源是邮件发信收尾轮询，第三是今日发送数统计。他说：「开吧，下一条」。

````
```
先快速修好发信收尾轮询反复读已发完记录的问题。同时把整个邮件系统里用到数据库的地方查一遍，找出不合理、给数据库加了过多压力的，SQL、索引、表结构都看，列成清单给他。
怎么算做到：收尾轮询只读还没发完的记录，走索引，单次在毫秒级，上线前后的单次耗时和读行数有对比；清单按「全表扫描、缺索引、扫描行数远大于返回行数、单次超过 1 秒、表结构让查询必须扫大范围」这几条查，每条写在哪、现在多重、建议怎么改。达标线拿不准的由接单的会话按业内做法定，写明依据。
范围：邮件系统；不做：别的模块，清单里的问题先不改，等他定。
已知：Joe 昨晚 20:59 在研发部群贴的两张截图，开工先核对现在还是不是这样。
```
我补的：① 收尾轮询的达标线 ② 清单按哪几条查 ③ 清单里的先不改
别的理解：A 只修截图里这两处 ／ C 再加一层，以后新写的慢查询能先发现或拦住
````

他 11-24 说的原话：「这个收尾可能是我们发现的其中一个邮箱系统的点，那我希望先快速修复这个，同时做类似排查，整个邮件系统里面涉及到数据库的，有没有不合理导致过度增加数据库压力的，不管是表结构还是索引还是sql」。当时的派单只写了这台主库的水位，做完才发现不是他要的。

## 和别的 skill 的关系

- `raise-target`：大总管派单前写完整派单用，照旧。他点名要「优化 prompt」时用本 skill。
- 本 skill 只管把话写清楚。写完他说「派」，再按 `hub` 的派单步骤走。
