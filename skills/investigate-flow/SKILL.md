# 排查流程

用户的做法：看到问题后，先查聊天记录、收集具体问题，再排查并拿出有论据的分析，然后一条一条过根因和改法，定了就开工，做完验收上线。下面四步是 2026-11-04 和用户逐条定下的。

## 总规则

- 和用户一条一条过，不让用户读长文件。超过 30 行的内容写文件作底档，汇报时在对话里逐条讲。
- 固定的 5 个确认点，到了就停下等用户：
  1. 问题清单确认（第 1 步结束）；
  2. 每个根因的改法（第 3 步）；
  3. 任务单「开工」（第 3 步结束）；
  4. 「上线」（第 4 步验收后）；
  5. 回复报问题的人之前的「发送」。

  另外两种情况也要问：任务单没授权的操作（先标「卡住」，做别的项，攒在一起问）；超出任务单范围的情况（见「上线」）。没有别的项可做时，把要问的一次问全再停。除此之外不停下问。
- 一个会话只做这一件事。讨论中冒出的新需求，在对话里记一句，另开会话，或者开会话写清楚后放进侧边栏「待开工」分组。
- 被 hook 拦下：拦截消息给了改法的，照改；没给改法的不换写法绕过，这一项标「卡住」，把要执行的命令交给用户。

## 第 1 步：收集问题

- 自己去飞书读原文（`lark-im` skill），不经过幕僚。事项来自幕僚的，会话标题可以带上幕僚的编号。
- 交出问题清单，每条写：谁报的、什么时间、原话、原消息链接、相关 ID 或截图、影响是否还在持续、哪里还不清楚。
- 每条再写「什么证据算回答了这个问题」。能改写成「是 / 否」的就改写，例如「进 spam 是不是签名的问题」改成「同一账号、同一封信，只换签名，Gmail 落点有没有差别」；原因、范围、影响类的问题，写清需要哪些证据。
- 停下：清单和「什么证据算答案」一起给用户确认，确认后再进第 2 步。影响还在持续的，在清单开头标出来；止血操作同样要用户批准。

## 第 2 步：排查

- 找根因的方法按 `debugging-discipline`（对立假说、证伪测试、读实现不读符号名）。pipeline 积压类按 `pipeline-debug-protocol`。
- 每条结论标证据强度：
  - **已证实**：有直接证据，例如日志、代码加实际执行结果、对照实验结果；
  - **相关**：数据方向一致，但证明不了因果；
  - **推测**：没有直接证据。

  结论那一句只写已证实的；相关和推测放在「线索」里。
- 只有相关性证据时不回来交差。先走完不花钱、不动生产的路：现有数据、追踪记录、测试环境、本地复现，拿到直接证据再回来。中途只在三种情况回来找用户：
  - 要花钱或要动生产；
  - 要向同事要信息；
  - 不花钱、不动生产的路都走完了，仍拿不到直接证据：报「证据不足」，写清缺什么证据、要什么条件才能拿到。

  回来时说清楚下一步实验测哪个假设，结果是 A 说明什么，是 B 说明什么。
- 交给用户之前，每次都过独立复核（见下节）。被推翻的结论改掉或降成线索；判「证据不足」的补证据或降档。
- 交出：结论（已证实）、线索（相关 / 推测）、复核结果。在对话里一条一条讲。

### 独立复核（默认用 Codex）

1. 把结论和每条结论的证据写进一个文件。只写结论、证据、数据口径和时间窗口，不写排查过程和你的推理。
2. 运行 Codex（只读沙箱，约 30 秒到几分钟，长的用后台运行）。路径放进变量，参数加引号：

   ```bash
   CLAIMS=/tmp/<主题>-claims.md; OUT=/tmp/<主题>-review.md; REPO="<仓库目录>"
   codex exec -s read-only --skip-git-repo-check --ephemeral -C "$REPO" -o "$OUT" "读 $CLAIMS。对每条结论找反例：证据能不能推出结论；时间窗口和数据口径对不对；有没有别的原因能解释同样的现象。每条判「成立 / 推翻 / 证据不足」，写出理由；需要时可以读仓库代码核对。用中文回答。" </dev/null
   ```

3. 读 `$OUT`。命令失败或没有结果时重试一次。仍失败，改用不带上下文的 Claude 子 agent 复核：description 以 `[独立验证]` 开头，model 和 effort 按 AGENTS.md「子 agent 选模型」显式写出。汇报里写明 Codex 失败的原因。
4. 两条路都失败：结论标「未复核」，作为阻塞报给用户，不当作已通过。

## 第 3 步：逐条过根因和改法

- 一次只过一个根因：给 2–3 种改法，写清各自代价，标出推荐。用户定了再过下一个。
- 离开第 3 步前定完任务单（模板见下）。每项附一句「为什么」，隔几天再看也能看懂。在对话里逐项过给用户，用户说「开工」才动手。

### 任务单模板

1. **根因和改法**。
2. **完成标准**：单测之外，在哪个测试环境、跑什么端到端场景、看到什么算通过。开工前先核对：
   - 测试环境是否空闲；
   - 测试库的迁移是否和要测的代码一致；
   - 共享资源会不会被别的环境抢走。避不开时写明替代验证路径，验收时标出这条路径覆盖不到什么。

   ordo_ai 的例子：用 `scripts/env_claim.sh status` 查空闲环境，`workday` 只占到当天 20:00，过了 20:00 按时长占；test1–test4 共用测试库和 Gmail 推送订阅，测试信可能被别的环境取走，11-02 用补录工具在指定环境重放代替。
3. **要用户动手的事**：步骤写清楚，标明在开工前做还是验收时做。步骤要实际核对过（看过界面或文档），没核对的标 [未验证]。
4. **上线范围**：重启哪些服务，为什么。
5. **数据修复**：要不要补数据，不补有什么后果，怎么补（在哪台机器、跑什么）。
6. **回复报问题的人**：回复哪条原消息，写什么。

## 第 4 步：执行、验收、上线

### 执行

- 用户说「开工」就开工，不等晚上。
- 执行中不停下问。遇到任务单没授权的操作（例如改共用测试库），这一项标「卡住」并写原因，先做别的项，攒在一起问。
- 合并、生产部署、生产补数据、给同事发消息，都要用户在对话里批准；没批准时最多做到开 PR。
- 每条交给用户的进展消息（包括用户问「进度如何」时），开头先列任务单 6 项的状态：

  | 项 | 状态 | 说明 |
  |---|---|---|
  | 1 根因和改法 | 通过 / 部分通过 / 进行中 / 未开始 / 卡住 | 部分通过写没验证到的部分和替代证据；卡住写原因 |

  后面再写细节。
- 断网前由大总管（`hub`）暂停会话。收到恢复消息后，先确认中断前那一步和后台任务（子 agent、workflow、后台命令）的状态，再继续。

### 验收

- 做完后把本会话移到侧边栏「待验收」分组：`mcp__ccd_sidebar__list_groups` 查到分组 ID，再 `mcp__ccd_sidebar__move_sessions`（`session_ids: ["self"]`）。分组不存在或工具不可用时跳过，在汇报里说明。
- 验收汇报按完成标准逐条写结果和证据（日志、截图、链接）。
- 要用户亲自做的验收（看页面、发测试信），把链接、操作步骤和预期结果集中写在同一条消息里，等用户做完、记下结果。所有验收项有了结果，最后只问一个问题：上不上线。

### 上线

- 用户说一次「上线」，就按任务单的上线范围合并、部署、补数据，不再逐步问。
- 发布前核对生产上正在运行的版本，以及它和 main 之间别人还没发布的改动。
- 部署后先读各服务的错误日志，再看新逻辑在真实流量上的表现。
- 补数据先预演。预演出的范围和数量与任务单一致就直接执行；不一致，把差别报给用户，单独问。
- 超出任务单的情况单独问：要顺带发别人的改动、要多重启服务、出现新的遗留问题。「同意上线」不等于同意这些。
- 一起发布：由用户指定一个会话接管全部发版，其他会话停在合并前，不靠互相发消息协调。

### 收尾

- 按任务单第 6 项起草回复：在原消息下回复，用同事间的口吻，简要说原因、怎么解决的、对方需要做什么。给用户看，用户说「发送」再发。
- 释放这次占用的测试环境。
- 发完把会话移出「待验收」（`move_sessions`，`group_id: null`）。

## 依据

- 10-30 签名进 spam：排查停在相关性（回信率对比），没讲清付费实验测什么，当晚撤回一条用错时间窗口的结论 → 第 2 步的证据分档、不拿相关性交差、独立复核。
- 11-02 Gmail 收不到：用户发了约 30 条消息，约 11 条是在追问进度或缺的信息（有没有在 test 环境验证、哪个环境空闲、在哪里验证、为什么要补录、谁提的问题）→ 任务单 6 项、进度表、验收汇报格式。
- 11-03 William 限额：两个会话互发消息协调「一起发布」，消息过期，用户连问「在发布了吗」「现在什么进度了」→ 一起发布由一个会话接管、上线只批准一次。
