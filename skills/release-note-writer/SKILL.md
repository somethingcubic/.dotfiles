# Release Note Writer

把一次发布翻译成"读者 30 秒能拿到他要的信息"的文档。**核心原则**：价值优先（用户能做什么），而非特性罗列（我们做了什么）。

---

## Step 1：决策树 - 先分类，再套模板

在写之前必须回答这 4 个问题。答完后跳到对应模板。

### Q1. 受众主要是谁？（决定语气和技术深度）

```
受众
├─ 外部用户（C 端 / B 端客户）       → 人话、收益、截图/GIF
├─ 内部团队（销售 / 客服 / 运营）     → 价值 + 话术 + FAQ
├─ 开发者（API / SDK 用户）          → 精确签名、迁移指引、版本号
└─ 混合                              → 分层：上半段人话，下半段技术
```

### Q2. 规模多大？（决定模板裁剪深度）

| 规模 | 判断标准 | 模板 |
|---|---|---|
| **Patch / 小功能** | <3 个变更点、无行为变更、单团队可消化 | [模板 A](#模板-a小功能--patch) |
| **Minor / 中型迭代** | 3-10 个变更、有新能力或行为变更、跨团队 | [模板 B](#模板-b中型迭代) |
| **Major / 旗舰版本** | 战略级 feature、营销联动、外部公关 | [模板 C](#模板-c旗舰版本) |

### Q3. 风险等级？（决定是否必须有 Breaking Change / 回滚 section）

```
风险
├─ 低：纯新增、可灰度、可一键关闭        → 标 "低"，简略说明 feature flag
├─ 中：行为变更、影响默认体验            → 必须列出"变更前 → 变更后"对照
└─ 高：Breaking Change / 数据迁移 / 安全 → 套 [模板 D](#模板-dbreaking-change) 强制段落
```

### Q4. 是不是紧急 Hotfix？

```
是 → 套 [模板 E](#模板-ehotfix--事故修复)，强调"影响范围 + 已恢复时间 + 后续动作"
否 → 走 A/B/C
```

### 特殊场景快捷入口

- **API / SDK 发版** → [模板 F](#模板-fapi--sdk-发版)（版本号 + 兼容矩阵 + 迁移代码）
- **内部工具 / DevOps** → [模板 G](#模板-g内部工具--平台)（操作步骤 + 回滚指令）

## Step 2：通用骨架（所有模板都包含）

写完套用对应模板前，先准备这些原料：

1. **一句话价值主张**：用户用了能**做什么** / 解决什么**痛点**
   - ❌ "我们重构了评论模块" → ✅ "评论支持 @ 同事，对方收飞书通知，不用再复制链接催人"
2. **发布元数据**：日期 / 影响范围（全量/灰度 X%/特定客户）/ 风险等级 / Owner
3. **可验证手段**：feature flag 名 / 监控看板 / 关联 PRD / PR
4. **反馈渠道**：群 / 邮箱 / 人

## 模板 A：小功能 / Patch

> 适用：<3 个变更点、低风险、单团队消化

```markdown
# 📌 [Feature Name] - vX.Y.Z

> [一句话价值主张：用户能做什么 / 解决什么痛点]

**发布日期**：YYYY-MM-DD
**影响范围**：全量 / 灰度 X%
**风险等级**：低（feature flag `xxx` 可关闭）

## 🎯 解决了什么问题
[1-2 句，非技术读者视角]

## ✨ 新增能力
- **[能力]**：一句话描述 + 用户收益

## 📋 使用方式
1. [步骤 1]
2. [步骤 2]

## 👥 反馈
- Owner：@PM / @Eng
- 反馈群：[链接]
- PR：#XXXX
```

## 模板 D：Breaking Change

> 适用：影响下游系统、需迁移、有 deadline

**必须包含的强制段落**（缺一不可）：

```markdown
# ⚠️ Breaking Change: [Change Name] - vX.0.0

> **行动要求**：[谁] 必须在 [Deadline] 前完成 [什么动作]，否则 [后果]

**生效日期**：YYYY-MM-DD
**强制截止**：YYYY-MM-DD（之后旧行为下线）
**影响范围**：[具体系统 / 接口 / 客户群]

## 🚨 什么变了
| 维度 | 变更前 | 变更后 |
|---|---|---|
| [字段/行为] | [旧] | [新] |

## 🛠️ 迁移指引（必读）
### 你需要做什么
1. [步骤 1，给代码片段]
2. [步骤 2]

### 如何验证迁移成功
- [ ] [检查项 1]
- [ ] [检查项 2]

### 迁移工具 / 脚本
[链接或命令]

## 📅 时间线
- D-30：通知 + 文档上线
- D-14：旧行为开始打 deprecated 警告
- D-0：旧行为下线

## 🆘 兜底
- 应急联系：@oncall
- 紧急回滚：[流程]
- FAQ：[链接]
```

## Step 3：写完自查 - 反模式清单

提交前对照检查，命中即返工：

### ❌ 内容层面
- [ ] 标题/首句写的是"我们做了什么"而不是"用户能做什么"
- [ ] 用了"重构 / 优化 / 增强 / 改进"等空话，没有量化（前后对比数字）
- [ ] 只列 Jira 编号 / PR 编号，没有人话描述
- [ ] 技术术语堆砌（状态机、microservice、refactor）出现在用户面向段落
- [ ] "性能提升"没有具体数字（3s → 800ms 才有意义）

### ❌ 结构层面
- [ ] 没写发布范围（全量？灰度？哪些客户？）
- [ ] 没写 Owner 和反馈渠道
- [ ] Breaking Change 没单独段落、没 deadline、没迁移代码
- [ ] 一次塞 20 个无关 feature，读者抓不到重点（应拆分或按重要度排序）
- [ ] 没有回滚说明 / feature flag 名

### ❌ 受众错配
- [ ] 给外部用户的 release note 写了"重构了 internal 状态机"
- [ ] 给开发者的 SDK note 没写代码 diff
- [ ] 给销售/客服没给话术模板和 FAQ

## Step 4：常用元素速查

### 一句话价值主张公式
> [用户角色] 用了这个能 [具体动作]，从此告别 [旧痛点] / 实现 [新收益]

例子：
- "管理员一次导入 1000 条客户数据，告别 Excel 逐条录入"
- "支持 @ 同事，对方收飞书通知，评论不再需要二次群里催"

### 风险等级速判

| 等级 | 判定 | 必须项 |
|---|---|---|
| 低 | 纯新增 + 可灰度 + 可关闭 | feature flag 名 |
| 中 | 行为变更 + 默认开启 | 变更前后对照表 |
| 高 | Breaking / 迁移 / 安全 | 模板 D 全套 |

### 影响范围标准写法
- `全量用户`
- `灰度 X%`
- `仅 [客户名/标签] 启用`
- `仅 [region] 启用`
- `内测：[用户列表]`

### 衡量指标常见维度
- 业务：转化率 / 留存 / DAU / GMV
- 体验：加载时长 / 错误率 / NPS
- 效率：单次操作耗时 / 工单量
- 技术：P99 延迟 / 资源占用

## Step 5：飞书渲染优化（重点）

普通 Markdown 在飞书里渲染会"灰扑扑"。飞书有自己的视觉元素，用对了 release note 一眼能抓到读者注意。

### 5.1 选择发送载体

| 载体 | 适用 | 特点 |
|---|---|---|
| **飞书云文档** | 正式 release note，需归档 / 转发 / 评论 | 支持高亮块、表格、代码块、待办、@、图片 |
| **群消息卡片**（Interactive Card）| 群内一次性广播，要求一目了然 | JSON 结构、可加按钮（跳转/反馈）、彩色头部 |
| **群消息（纯文本/简单 markdown）** | 内部小群快讯，无需精致 | 仅支持极简 markdown，emoji + 缩进为主 |

**决策**：
- 受众 > 50 人 / 需要长期查阅 → **云文档** + 群里发链接卡片
- 受众 < 50 人 / 一次性同步 → **消息卡片**
- 极简快讯（如 "v1.2.3 已上线"）→ **群消息**

**默认输出规则**：
- 用户说"飞书能发的格式"、"飞书群里发"、"直接贴飞书"时，默认输出 **5.5 飞书群消息精简版**，不要包在 markdown 代码块里，不要使用 `#`/`##`/表格/引用块。
- 用户说"飞书好看一点"、"正式一点"但没有要求直接复制粘贴时，优先建议 **消息卡片**；如果不能直接发送卡片，先给 **5.5 精简群消息**，再附一句"更好看的版本建议用消息卡片/云文档"。
- 用户明确说"飞书文档"、"归档"、"长文"时，输出 **5.3 云文档版**，并用自然语言标注哪些段落应放到高亮块/表格/折叠块，而不是只给 GitHub markdown。
- 用户要求"不要 markdown"时，输出纯文本版，避免 fenced code block 和 markdown 标记；可以保留 emoji、树形符号、全角冒号和空行。

### 5.2 飞书云文档渲染指南

飞书云文档的"加分元素"，优先使用：

#### ① 高亮块（Callout）- 替代普通段落
飞书有 5 种颜色高亮块，对应不同语义：

| 颜色 | Emoji | 用途 |
|---|---|---|
| 🟦 蓝色 | 💡 / ℹ️ | 普通信息 / 价值主张 |
| 🟩 绿色 | ✅ / 🎉 | 新增能力 / 成功修复 |
| 🟨 黄色 | ⚠️ / 📌 | 注意事项 / 行为变更 |
| 🟥 红色 | 🚨 / ⛔ | Breaking / 故障 / Deadline |
| 🟪 紫色 | 💭 / 🔮 | Tips / 后续路线 |

**写法**（在飞书云文档编辑时）：`/` 唤出菜单 → 选"高亮块" → 选颜色 → 粘内容。如果是通过 API/lark-doc 写入，用 `callout` block type。

#### ② 表格代替罗列
飞书表格渲染极佳，能用表格的别用列表：

```
| 维度 | 变更前 | 变更后 | 影响人 |
|---|---|---|---|
| 评论 @ | 仅复制链接 | 直接 @ 同事 | 全员 |
```

#### ③ 待办列表（Checkbox）
迁移指引、Owner 行动项用 `[ ]` 待办格式 —— 飞书里可以打勾，状态实时同步。

#### ④ 锚点 / 目录
长文档开头放"目录"块（飞书自动生成），方便 H 系列读者快速跳转。

#### ⑤ @ 提及
Owner / 反馈联系人用 `@ 张三` 真实 @，对方会收通知。

#### ⑥ 折叠块
技术细节、FAQ、完整 changelog 放折叠块，避免压缩主线信息。

### 5.3 飞书云文档版模板（小功能示例）

> 这是模板 A 的飞书优化版，可直接通过 `lark-doc` skill 写入飞书云文档

```
📌 评论支持 @ 提及同事 - v2.14.0
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🟦【蓝色高亮块】
💡 在评论里直接 @ 同事，对方收到飞书通知，不用再复制链接到群里催人看了。

📋 发布信息
┌─────────────────────────────────────┐
│ 发布日期：2026-05-11                 │
│ 影响范围：全量用户                    │
│ 风险等级：🟢 低（feature flag 可关闭）│
│ Owner：@张三 / @李四                  │
└─────────────────────────────────────┘
（用真正的飞书表格渲染上面这块）

🟩【绿色高亮块】
✨ 新增能力
• @ 选人：评论框输入 @ 弹出同事列表
• 飞书通知：被 @ 的人收到飞书卡片
• 未读提醒：右上角铃铛显示未读数

🟨【黄色高亮块】
📌 使用方式
☐ 1. 评论框输入 @
☐ 2. 选择同事
☐ 3. 发送

▼ 技术注记（折叠块，默认收起）
└─ Feature flag：comment_mention_enabled
└─ 关联 PR：#4821
└─ 已知限制：暂不支持 @ 群组

💭【紫色高亮块】
💬 反馈渠道
• 飞书群：[评论 feature 反馈群]（点击加入）
• Owner：@张三（PM）
```

**渲染要点**：
- 价值主张用 🟦 蓝色高亮块包起来 —— 飞书顶部一眼看到
- 新增能力用 🟩 绿色 —— 喜事
- 使用方式用 🟨 黄色 + 待办 checkbox —— 用户可以打勾
- 技术注记折叠 —— 避免干扰用户视线
- 反馈用 🟪 紫色 —— 友好结尾

### 5.4 飞书消息卡片版（群广播）

```json
    "title": { "tag": "plain_text", "content": "📌 评论支持 @ 同事 - v2.14.0" },
    "template": "blue"

  "elements": [
    {
      "tag": "div",

    { "tag": "hr" },
    {
      "tag": "div",
      "fields": [
        { "is_short": true, "text": { "tag": "lark_md", "content": "**📅 发布日期**\n2026-05-11" } },

        { "is_short": true, "text": { "tag": "lark_md", "content": "**⚠️ 风险等级**\n🟢 低" } },

      ]
    },
    { "tag": "hr" },
    {
      "tag": "div",
      "text": {
        "tag": "lark_md",
        "content": "**✨ 新增能力**\n• @ 选人弹出同事列表\n• 飞书卡片通知 + 跳转\n• 未读铃铛提醒"
      }
    },
    {
      "tag": "action",
      "actions": [
        {
          "tag": "button",
          "text": { "tag": "plain_text", "content": "📖 查看完整 release note" },
          "type": "primary",
          "url": "https://docs.feishu.cn/xxx"
        },
        {
          "tag": "button",
          "text": { "tag": "plain_text", "content": "💬 反馈问题" },
          "type": "default",
          "url": "https://feishu.cn/chat/xxx"
        }
      ]
    }
  ]
}
```

**header.template 颜色**（对应风险/类型）：
- `blue` 普通发布 / 新功能
- `green` 已修复 / 性能优化
- `yellow` 行为变更 / 注意事项
- `red` Breaking Change / Hotfix
- `purple` 旗舰版本 / 重大更新
- `turquoise` 内测 / Beta

**字段技巧**：
- `<at id=open_id></at>` 真 @ 人（需要 open_id，可用 `lark-contact` skill 查）
- `fields` + `is_short:true` 实现两列网格，比文字罗列紧凑
- `action` 按钮放跳转链接，比纯文本可点击性强
- `lark_md` 支持飞书 markdown 子集（粗体、链接、@、emoji）

### 5.5 飞书群消息精简版（IM 文本）

适用：极简快讯。飞书 IM 仅支持极少 markdown，靠 emoji + 缩进结构化。

```
🚀 v2.14.0 已上线｜评论支持 @ 同事

💡 价值：评论里 @ 人，对方收飞书通知
📅 时间：2026-05-11 全量
🎯 范围：全量用户
⚠️ 风险：🟢 低

✨ 新能力
  ├─ @ 选人
  ├─ 飞书通知
  └─ 未读铃铛

📖 详情：https://docs.feishu.cn/xxx
💬 反馈：@张三
```

**要点**：
- 第一行 emoji + 标题 + 版本号，群消息列表里一眼可识别
- 用 `┌─ ├─ └─` 树形符号替代缩进列表（飞书不渲染 markdown 嵌套）
- 链接和 @ 用纯文本，让飞书自动识别

---

### 5.6 飞书渲染反模式

- ❌ 直接把 GitHub markdown 粘进飞书云文档 —— `###` 标题渲染不如直接用飞书的 H1/H2/H3 块
- ❌ 用 `>` 引用块装价值主张 —— 飞书引用块视觉权重低，**改用蓝色高亮块**
- ❌ 长段落不分块 —— 飞书读者眼睛会跳过
- ❌ 在 IM 消息里贴 markdown 表格 —— 渲染会糊成一坨，改用树形符号 / fields 卡片
- ❌ Owner 只写姓名没 @ —— 真 @ 才有通知
- ❌ 消息卡片 `template` 颜色随便选 —— 颜色有语义，乱用会误导
- ❌ 文档里贴大段代码 —— 用折叠块包起来或贴 PR/Wiki 链接
- ❌ 全部用 emoji 标题（如 🎉🎉🎉 v2.0🎉🎉🎉）—— 显得不专业，重要 emoji 在每段开头各用一个就够

### 5.7 配套 skill 调用

写完后用以下 skill 实际发布：

| 目标 | Skill |
|---|---|
| 写飞书云文档 | `lark-doc`（创建文档 + 写入 markdown / blocks） |
| 发消息卡片到群 | `lark-im`（发送 interactive 消息） |
| 把 PM/Owner 真 @ | `lark-contact`（查 open_id） |
| 文档归档到知识库 | `lark-wiki`（挂到知识空间节点） |
| 上传演示 GIF / 截图 | `lark-doc` 或 `lark-drive`（上传后嵌入文档） |
| 画架构图 / 流程图 | `lark-whiteboard`（生成图嵌入文档） |

**典型 pipeline**：
```
1. 用本 skill 决策树 + 模板 → 产出 markdown 草稿
2. 转换为飞书优化版（套 5.3 渲染风格）
3. lark-doc 创建云文档 → 写入内容
4. lark-im 发卡片到群，按钮链接指向云文档
5. 重要 release 用 lark-wiki 挂到产品知识库
```

## 使用流程总结

```
1. 走决策树（受众 / 规模 / 风险 / 紧急度）→ 确定主模板
2. 准备通用骨架原料（价值主张 / 元数据 / 验证手段 / 反馈）
3. 套对应模板（可叠加：A + D 表示"小功能但含 Breaking"）
4. 反模式清单自查
5. 如发到飞书：选载体（云文档 / 消息卡片 / IM）→ 套 5.3-5.5 渲染优化
6. 调用配套 skill（lark-doc / lark-im / lark-wiki）实际发布
7. Owner / PM / 上线团队 review 后发布
```

**叠加示例**：
- 小 feature 但含 Breaking → 模板 A + 模板 D 的"Breaking 段落"
- 旗舰版本带 SDK 升级 → 模板 C + 模板 F 的"Added/Changed/Deprecated"
- Hotfix 涉及 API 行为变更 → 模板 E + 模板 D 的"迁移指引"
