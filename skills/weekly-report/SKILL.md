# 写周报

用户负责 Ordo 邮件模块，现在是三行：Brand 邮件、SSG 邮件、整合通讯（探索）。周报是「Ordo研发部」群里发的飞书文档「OrdoAI 周报」，每周一节（11-02 起每周拆成独立文档），表格一行一个模块。读的人是 CEO、CTO 和业务负责人：他们要知道做成了什么、问题能不能解决、哪天解决、要什么资源。

每次开写前先读知识库的 `~/Documents/AgentVault/user/weekly-report.md`：里面有群里的要求原文、被表扬的范例行、用户历次的定稿（第一份是 10-30）。这些含同事名字和业务数据，只放在私有知识库里，不写进本 skill。写完一周，问用户要不要把这周的定稿和新出现的要求追加进去：白天改知识库要用户同意（AGENTS.md「知识库」）。

## 总规则

- 在对话里一条一条过，不让用户读长文件（AGENTS.md「沟通与输出」）。提纲、素材、初版、定稿都写成底档，放在会话文件夹里。
- 到下面这几处就停下，等用户回复：
  1. 提纲（第 2 步）；
  2. 定稿（第 5 步），用户说「填」再填表；
  3. 把链接或消息发给别人之前，用户说「发送」再发。
- 只写用户分工里的模块，别人的行不碰。群里对所有人提的格式要求，先确认对哪些模块生效。10-30 群里说「业务的统一放最上面」，指的是产品模块，邮件模块的行不加【业务】前缀。
- 中途做出来的东西（例如一份分布统计），用 SendUserFile 单独发给用户，并在对话里逐条讲要点；不要只在长消息里附一个文件链接。
- 后台收集用 workflow 或子 agent，description 以 `[并行只读]` 或 `[大范围读取]` 开头，model 和 effort 按 AGENTS.md「子 agent 选模型」写明。启动时当场说它在查什么、预计多久。

## 第 1 步：读要求和范例

1. 读群里本周的要求：
   - 找群：`lark-cli im +chat-search --query "Ordo研发" --as user --profile ordo`
   - 读消息：`lark-cli im +chat-messages-list --chat-id <群ID> --order desc --page-size 50 --no-reactions --as user --profile ordo`
   - 截图要下载下来看：`lark-cli im +messages-resources-download --type image --message-id <id> --file-key <key> --output lark-img/<名字>.png`。10-30 的要求有一半写在截图里，例如月报注意事项。
   - 记下四样：文档链接、本周那一节的位置、表头和填写说明、字数或格式要求。
2. 读文档：`lark-cli docs +fetch --doc <链接>`。看表头下面的填写说明。上一周用户自己写过的那几行也要读出来：上周「下周计划」里的每一项，这周都要交代做到没有。
3. 找范例：群里被表扬的那一行（10-30 是「视频内容审稿」那行）。要求和范例当天还会变，开写前、填表前各重读一次群消息。记下范例的格式和每格字数，作为篇幅的参照。群里没人被表扬时，参照同一张表里其他人的篇幅。

## 第 2 步：先和用户过提纲

不对齐方向就开始收集，用户会叫停（10-30：「周报你打算收集哪些材料，思路是什么，打算说哪些东西，先和我过」）。在对话里列：

- 打算收集哪些材料、从哪里收集；
- 每个模块打算讲哪几件事，每件一句话：做成了什么、数据是什么、还差什么；
- 上周计划的完成情况。

停下：用户改完提纲再往下做。

## 第 3 步：收集素材，核事实

时间窗口是本周一 00:00 到当天，北京时间。素材来源：

- **用户本周发的飞书消息**：`lark-cli im +messages-search --sender <用户 open_id> --start <周一>T00:00:00+08:00 --end <今天>T23:59:59+08:00 --page-all --as user --profile ordo`，翻页读满。用户的 open_id 用 `lark-cli auth status --json --profile ordo` 查。
- **哪些改动已经上生产**：机器人发的上线卡片，`lark-cli im +messages-search --query "上线通知|发布|已上线" --sender-type bot --start <周一>T00:00:00+08:00 --end <今天>T23:59:59+08:00 --page-all`。没有上线记录的，只能写「已完成」，不能写「已上线」。
- **代码**：涉及的仓库（ordo_ai、ordo-platform 的 Brand、aidd-mail-desk）按时间窗口跑 `git log` 和已合并的 PR。
- **知识库**：AgentVault 里相关项目的 `status.md`，以及本周的 `journal/`。
- **伙伴 agent 的记录**，用来核对提纲：
  - 用户的两个私聊；
  - 事项库 `~/tasks/partner/state/partner.db`，只读打开：`sqlite3 "file:<路径>?mode=ro&immutable=1"`。
  - 用户原话：「他一直在做我本周所有工作的监控」。10-30 用这份记录找出了提纲里 4 处错误。
- **重点产品的使用数据**（10-30 是 Brand 邮件）：按业务流程一路看到回信内容、报价和客户后续动作，不能只数发信量。样本小就逐条看。先排除内部同事代操作的租户和测试租户。
- **引用的外部数字**：查清出处和适用范围再用。10-30 写的「行业约 68%」，查下来是 B2B 销售回复买家邮件的比例。用户定保持不动，但这件事要在提纲阶段就讲清楚。

写成底档 `周报素材-<模块>.md`。提纲里和素材对不上的地方，逐条告诉用户。

## 第 4 步：照范例写

**格式**（照 10-30 的范例行）：

- 第一格：模块名，后面 @负责人（10-30 群里的要求：「事项后面@你自己 就可以」）。
- 本周进展：先写「目标：① …；② …；③ …。当前阶段：…」，再按 a、b、c 写进展，每条末尾标它对应的目标，例如「（目标 ①）」。
- 下周计划：按 1、2、3 编号，每条写「日期 + 做到什么样」，不超过 5 条。
- 问题、风险与资源：「风险 1. … 2. …｜资源 1. …」，风险和资源分开写。

**写法**（括号里是 10-30 的纠正）：

1. 每条进展写结果和数据：多少人用、多快、多好用、多难用。不写只描述现象的句子。
2. 每个问题和风险都写能不能解决、怎么解决、哪天解决、依赖谁（「只描述现象，不说我们能不能解决，打算多久解决，这种汇报是没意义的」）。
3. 不写 PR 号和技术名词，按业务能看懂的话写（「10-29 #1545 这种业务看不懂也没必要懂」）。写完扫一遍残留，正则参考：`#[0-9]|warn|bedrock|spf|dkim|dmarc|rds|redis|kafka|线程|提示词|token|api`。
4. 不拿同事的反应当成果（初稿写了「几位同事都想用」，用户：「你周报能这么写吗？」）。探索项写要解决的问题、已经验证的、还没验证的、哪天给结论。
5. 排期先读代码再估，不照搬旧计划、每步加缓冲（「这个为啥要这么久」）。写完所有日期，逐条再核一遍。
6. 开关和范围这类决定（例如开给谁），先用数据看分布再给建议，不默认缩到试点（「提醒应该对所有人都开啊……你先统计一波」）。
7. 小项不为了压篇幅删掉，并进「其他」那一条（「要加回来」）。
8. 篇幅照范例来。三行写完数字数：去掉标签，数进展、计划、风险与资源三格的字数，含标点，和范例并排给用户看。10-30 范例 401 字；用户定稿 Brand 405 字、SSG 705 字、整合通讯 197 字；初版三行一共 2,473 字，被说「啰嗦」。超出很多时，按 10-30 找到的 5 个原因压：
   - 进展里又写了一遍计划的日期，日期只放在计划列；
   - 一条里塞了背景、原因、数据、方案，原因和细节留给复盘；
   - 条目太多；
   - 目标行带了解释；
   - 风险写成了完整的方案句。
9. 详细报告要附链接时：用 `htmldrop` 发布，把链接贴在对应的那句话上。只发能单独打开的页面；正文链到本地附录文件的报告，发布后链接会断。

写成底档 `周报初版-<模块>.md`。之后每一版都覆盖这份文件。

## 第 5 步：过定稿，填表

1. 在对话里逐行给用户看定稿：每行三格，每格标字数。用户说「填」再填。
2. 填表（先读 `lark-doc` 的 update、xml、style 三份参考）：
   - 取带块 ID 的表格结构：`lark-cli docs +fetch --doc <链接> --scope section --start-block-id <本周研发小节的块ID> --detail with-ids`
   - 行不够就自己插行，不让用户去手动插（「行数该加就加」）：`lark-cli api PATCH /open-apis/docx/v1/documents/<文档ID>/blocks/<表格块ID> --data '{"insert_table_row":{"row_index":<位置>}}'`
   - 逐格写入：`lark-cli docs +update --doc <链接> --command block_replace --block-id <单元格块ID> --content -`
   - 改已有内容：先 `block_delete` 删掉多余的块，再 `block_replace` 换掉第一块；只改一句时用 `str_replace`。
   - 别人可能同时在编辑。插行前重新取一次表格结构；撞上了（例如同一位置被别人插了一行），就换位置另插一行，不覆盖别人的行。
3. 回读核对：重新 fetch，逐格核对字数和关键句，链接要能打开。
4. 报给用户：填在哪一节、哪几行、每行字数，以及没核对到的地方。
