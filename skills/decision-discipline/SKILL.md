# Decision Discipline: 场景驱动，不钻牛角尖

本规则用于提醒 agent 在做技术方案、spec、review、上线运维方案时，不要把工程洁癖、抽象欲或平台化想象凌驾于真实场景之上。

## 核心判断

- 工程洁癖是必要的，但必须服务真实业务场景；不是所有状态都要表化，不是所有重复都要抽象，不是所有风险都要平台化。
- 先问“这是业务状态，还是一次执行过程的便利状态？”业务状态才进入长期模型；执行便利优先用参数、日志、文件、脚本、tmux/supervisor/systemd 状态承载。
- 平台化只在需求流证明它会复用时成立：同一方向连续出现 3 次以上，或已经明确未来 2-3 个 checkpoint/feature 共享同一生命周期问题（调度、断点、重试、观测、权限、审计）。
- 短期 feature、一次性 backfill、POC 验证、临时抽样，不要为“未来也许”设计框架；先用最短闭环打通，保留可演进出口。
- 如果抽象成本高于下一次复制成本，先复制；等真实重复出现再抽象。

## 加表/平台化前自问

1. 这个状态 3 个月后谁会读？谁会写？是否会进入产品、搜索、权限、审计或运营流程？
2. 它是事实画像/业务资产，还是某次任务的 cursor、进度、临时 checkpoint？
3. 不加表，用启动参数、日志 cursor、文件记录、一次性脚本能否满足当前风险？
4. 现有需求是否已经证明多个维度共享同一套调度/断点/重算/观测能力？
5. 做平台化后，是否会让当前最短路径变慢、变脆、需要更多迁移/联调/上线顺序？

## 当前锚点

- `update_frequency` 画像本身是长期业务资产：会被搜索、分层和运营理解使用，放 Data Center RDS 的画像表是合理的。
- `update_frequency` 首批 backfill cursor 是执行便利状态：当前不应再加 checkpoint 表；优先用 `start_cursor`、`run_once`、日志中的 cursor、分批命令和人工/脚本续跑解决。
- 后续如果多个画像维度都需要同一套“初始 backfill + 增量重算 + 优先级队列 + 可观测”能力，再讨论通用派生画像调度平台。
