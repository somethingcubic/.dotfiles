# 调研流程

用户的做法：给一个目标，很多时候只是一个想法，还没想清楚。AI 先帮用户想清楚要什么，带着自己的思路，方向放得开，再权衡着深挖。下面四步是 2026-11-05 和用户逐条定下的。

## 总规则

- 沿用 `investigate-flow` 的总规则：一条一条过，不让用户读长文件；一个会话只做一件事；被 hook 拦下的处理。
- 本流程固定的确认点，到了就停下等用户：
  1. 调研单（第 1 步结束）；
  2. 交付后要用户定的 2–3 个点（第 3 步）；
  3. 结论的去向（第 4 步）；
  4. 把结论或链接发给别人之前的「发送」。
- 调研只读：除了写底档，不改代码、不提交、不开 PR、不改配置、不装东西、不删文件。要花钱（付费 API、付费数据）或动生产才能拿到的证据，停下问用户，说明下一步测哪个假设、结果是 A 说明什么、是 B 说明什么（同 `investigate-flow` 第 2 步）。
- 要用户批准的事，每项单独列出；用户的回复只对点名的项生效。回复是「go」「继续」这类时，先复述你理解的范围再动手。
- 估时：派子 agent 写的预计按实测打折（调研除以 3），见 AGENTS.md「派单按工作量估时」。给用户报「给出结论约 X」。
- 用户中途纠正定义、视角或用途（想法变了），先改调研单第 1、3 项给用户确认，再接着查。

## 第 1 步：帮用户想清楚，定调研单

用户给的往往只是一个想法。先帮他想清楚要什么，再开查。拿具体的东西让用户挑、让用户反驳，比连续发问有效。

按轮进行，每轮最多 3 个问题，尽量用 AskUserQuestion 的选项卡片。

- **第 1 轮：复述，带上你的思路，问用途。**
  - 用自己的话复述这个想法，说出你猜的触发点：用户看到了什么才想到它。
  - 先给你自己的初步判断和 3–5 个可能方向，其中至少 1 个非常规的。
  - 问结论拿来做什么，给 2–3 个猜测让用户选。例如「达人商业价值」可能是：A 省更新的钱，弄清哪些达人不用刷新；B 在没合作过的达人里找新人；C 给业务同事一个挑人的标准。
- **第 2 轮：检验结论会不会改变做法。**
  - 针对用户选的用途问：结论是 X 你会怎么做，结论是 Y 你会怎么做。两种结论下做法一样，说明查了也改变不了决定，直接说不值得查，或者建议换一个问题。
  - 问用户现在的直觉（猜答案是什么）和最担心的情况。调研要专门去验证或推翻它。
- **第 3 轮（用户还说不清时才走）：先摸底，再问。** 花 10–15 分钟快速看：自己的数据大概是什么样，外部有没有现成做法。带 3–5 条看到的东西回来，再问一轮。

目标本来就清楚的，第 1 轮直接给调研单，不硬走三轮。「清楚」指用户已经说出结论要改变哪个决定，而且没有把核心概念的定义留给你。例如「Gmail 把这个发件地址判成垃圾，有什么办法」算清楚；「分析达人的商业价值」不算，因为「商业价值」怎么定义留给了你。

收敛成调研单，6 项：

1. **目标和用途**：用户原话，以及结论拿来定什么。用户没说的，填推荐值并标「原文没写，这是我的推荐」。
2. **问题**：用户原话里有几问就列几问，每问写「什么算答完」。
3. **用户的假设或体感**：没有就写「没有」。
4. **范围**：查哪些来源（自己的数据和代码、外部成熟做法、开源项目、相邻行业），不查什么。问题属于「该怎么做」的，默认查外部成熟做法。别的 agent 写的 spec 或派单加进来的范围、问题、必写章节，单独列出来给用户看；spec 回来后对照调研单逐项核，多出来的删掉或问用户。
5. **前提**：结论依赖的外部条件，例如要不到的 key、要找的人、要花的钱。
6. **产出和时长**：深挖几个方向（默认 3 个，另留 1 个名额给非常规方向）；预计多久；在对话里逐条讲，同时写底档；只读、不改代码。

停下：调研单给用户确认，确认后才开查。

## 第 2 步：放开列方向，便宜地初筛，集中深挖

列方向和初筛都便宜，不限范围；实测、跑数据、读原文贵，控制的是深挖的数量。调研单里「不查什么」只约束深挖：列出来的方向落在里面的，标出来，不提前删。

1. **列方向。** 派 3 个子 agent（description 以 `[并行只读]` 开头，model 和 effort 按 AGENTS.md「子 agent 选模型」写出），各列一份，互相看不到对方的结果，不设数量上限。每个方向一句话写是什么、为什么可能行。
   - 自己的数据和代码；
   - 外部成熟做法、开源项目、相邻行业；
   - 不受现有约束的大胆方向：反过来（不解决这个问题行不行、把问题交给别人），去掉约束（预算不限、只给一天、不用现有系统），换个层面（从流程或产品上解决，不从技术上解决）。
2. **初筛。** 合并去重后，每个方向只花几分钟，查三件事：有没有人做过；有没有证据确凿的硬伤；结论能不能改变用户的决定。砍掉一个方向必须写理由，只认三种：有证据的硬伤、不改变决定、被别的方向覆盖。「看起来太难」不算理由。
3. **深挖。** 按「对决定的影响」和「验证成本」挑，数量按调研单。

查法和执行细则：

- 技术选型、方案可行性类，按 `think-research` 的来源优先级和证据地图查。它的长报告模板只写进底档，不在对话里照念。
- 派子 agent 前，先核对写进派单的背景事实（查数据、代码或原始消息）。
- 结论分三档：已证实、相关、推测，定义同 `investigate-flow` 第 2 步。事实性的结论只写已证实的；建议可以建立在相关或推测的证据上，但要写明依据是哪一档。
- 外部资料只能说明「别人怎么做」时，同时给出在自己数据里怎么验证，并说明验证结果能不能改变决定。
- 派单写明只读。结束时在涉及的仓库跑 `git status`，有改动就停下报给用户，由用户决定留不留；不自己回滚，也不自己提交。
- 每次启动后台任务（子 agent、workflow、长命令），当场用一句话说它在查什么、预计多久。从第 2 步开查算起，超过 30 分钟的，每 30 分钟在对话里报一次进度：哪些方向查完了、正在查哪个、卡在哪。做完主动说。

## 第 3 步：交付

- 交付前每次都过独立复核：Codex 只拿结论和证据，逐条找反例。命令、文件写法（只写结论、证据、数据口径和时间窗口）和失败处理按 `investigate-flow`「独立复核」。判「推翻」的结论改掉；判「证据不足」的补证据，或者降成线索。
- 在对话里按调研单的问题逐个讲：
  - 每个问题第一句直接回答。先讲现状，再讲建议。每个问题都给建议，并说明值不值得投入。
  - 依据 2–3 条，标证据强度。推算出来的数字写明是谁算的、有没有独立复算。
  - 数字写精度，以及能不能拿来做决定。
  - 结论是一套方案时，写影响面和前提：在不在主流程上、碰哪些共享资源、什么条件下结论不成立。
  - 不用自造词。用户没说过的名词，包括你给方案、名单、批次起的名字，以及术语，第一次出现时用一句话写清它是什么、拿来验证什么。
  - 深挖的结果在对话里讲。全部方向和砍掉的理由放进底档，对话里只用一句话说砍了几个、分别因为什么；用户点名哪个，就把它捞回来。
- 最后只留 2–3 个要用户定的点，每个写选项、做了得到什么、不做损失什么、要花多少钱，再给推荐。用户说「我来挑」时，只列选项，不改文件。
- 全文写进底档。给用户或别人读的链接版只放结论、2–3 条依据和要定的点，一屏读完；全文另放详细版。链接用 `private-htmldrop` 生成；对外分享前，问用户要不要去掉公司名和内部名词。

## 第 4 步：收尾和去向

- 每个调研最后落到一个去处，给推荐，让用户选：
  - **要做成功能或规则**：开新会话走 `requirement-flow`。调研单和结论直接当需求来源，第 1 步不重新收集，只补空白。
  - **要排查**：开新会话走 `investigate-flow`。
  - **暂不做**：开会话写清楚，放进侧边栏「待开工」分组。
  - **不值得做**：把结论和理由记进底档，到此结束。
  - **还在探索、定不下来**：写清已验证和没验证的点、下一步值得深挖的方向、哪天能给结论。
- 不在调研会话里接着实现。转给新会话时：
  - 把调研单、结论和用户的决定写进底档。会话没选项目文件夹时，底档在 App 给这个会话临时建的文件夹里，删掉会话时文件夹也会被删，所以先复制到目标仓库的 `.tasks/`；没有目标仓库的，把调研单、结论和决定直接写进新会话的 brief。
  - 用 `mcp__ccd_session__start_session` 开新会话（App 会弹卡片让用户点），brief 写底档路径、要走的流程、用户已定的决定。
- 要给老板或同事看的：做成链接，开头先写结论和值不值得投入；发之前给用户看，用户说「发送」再发。
- 结论有长期价值的，问用户要不要「记到知识库」。

## 依据

- 10-08 达人商业价值：AI 把商业价值定义成「业务用过没有」，用户纠正「我找人除了发现已有的，更多还是在蓝海里面捞啊」；用户自己的假设是被纠正后才说出来的；用户问「所以你的建议是什么」「评论的真实性应该有开源的项目在做？」；目标换了 4 轮。
- 10-08 海外商单 hashtag：用户问「你是怎么去调研的？证据都有什么？」，首份结论里的推算值没有复算；文献推算和自己数据差一倍多；中间 2 个半小时没有汇报。
- 10-14 toto 仓库：原话三问，首份报告漏答「怎么实现的」；交的是本机路径。
- 10-15 公众号文章：用户问了 3 次进度；派单写了只读，执行会话仍改了代码。
- 10-24 好助手应该是什么样：调研前 AI 在给助手逐个补工具；报告被接受后用户才说「核心就是主动」。
- 10-27 告警：更简单的信号「No available accounts」是用户先提的；用户问「现在成熟的告警最佳实践是什么？」「这些改动有会影响到主流程的吗？」。
- 11-03 Gmail 过滤：派给子 agent 的背景事实有错，两路查偏。
- 11-04 人机协作调研：报告出来后用户才说体感，又问「你的调研支持这个吗？」；用户说「我不想看报告，你一条一条给我讲」。
- 外部做法：ChatGPT Deep Research 开始前可能先问澄清问题，再给可修改的调研计划（OpenAI 帮助页）；Gemini Deep Research 先展示调研计划卡片，确认后才开查（第三方使用指南）。
