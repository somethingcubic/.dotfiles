# 目标升维

Samuel 11-17 的原话：「在每次发布任务或者目标时，需要将该目标进行升维的思考从而优化 target」。他在 11-13、11-16 三次手动要求「优化一下目标深度广度高度速度，然后派工」，这份 skill 把那几次他认可的写法固定下来。

要解决的问题（11-11「找做浅了的案例」调研，两轮独立复核后的结论）：他往上一层的问题问得不少，缺的是把上一层写成一个由接单的会话负责、说得清怎么算做到的目标。所以这里产出的是一份写好目标的派单，不是多问他几个问题。

## 什么时候用

- 用：新需求、调研、他给的目标类任务（「把 X 做好」「X 上去」）。
- 不用：20 行以内的小改动、排查一个具体报错、纯查询。
- 谁做：大总管开会话前做一次。他不经大总管、直接在会话里给目标时，由 `requirement-flow`、`research-flow` 的第 1 步做。派单里已经有「原目标」或「直接目标」一行的，接单的会话不重做。

## 高度：原目标做完，他要的结果到手了吗

先用一句话写出原目标，再问一次「做完这件事，然后呢」，得到他真正要的结果。然后二选一：

- **结果仍然落空 → 升一层。** 原目标做完后，他要的结果还是没有。例：原目标是「来信被 Gmail 删除后清掉残留的摘要和标记」，做完后达人的报价照样看不到；升成「达人回信到过我方邮箱就不在 Ordo 里丢」。派单里两行都写：

  ```
  原目标（升维前）：<原来要做的事>
  升一层后的目标：<结果>。再往上的 <更高一层> 不在这次范围。
  ```

- **原目标做完就等于结果 → 不升。** 例：「40MB 的附件能发出去」。派单里写「直接目标」和「背后的目标」各一句，不扩大范围；完成标准按用的人能不能用来算（收件人真能下载到文件、信没进垃圾箱），不按代码写完算。

升后的目标怎么写：

- 写「建成什么、建到什么程度、怎么算做到」。尽量带数字，例如「上线后新增的『标着有来信、实际没有来信』会话数为 0」。起点还没量出来的，写「先量出现在是多少，目标值和用户一起定」。过程计数（监控先报了几件）只当依据，不当目标。
- 写清接单的会话对什么结果负责。
- 只升一层。再往上一层写一句「不在这次范围」。
- 原来要做的事是第一版，照常先交付；升出来的部分排在第一版之后（见「速度」）。例外：升后的目标要先量起点或先分清原因才能排顺序的，这一步放在最前面。升后仍是一个会话，占一个在制名额，不拆成几个会话。
- 另一个例外：升出来的部分进不进第一版，看会不会做两遍。先做升出来的部分能让原来的事只做一遍的，把它放进第一版；否则排在第一版之后。判断时数每个调用方要切几次、发布和验证要做几轮，不只看代码能不能复用。例：Firecrawl v1 迁 v2，升出来的是「ordo_ai 和 ordo_agent 共用一个统一入口」。先各自迁到 v2 再统一，每个调用方要切两次；先统一再迁，每个调用方只切一次。所以统一入口进第一版。
- 写一行退回原目标的条件，例如「核对后发现留底要改表结构，就只做第一版，留底列给用户定」。

这四种情况不升，在派单里写一句原因：

1. 上一层已经有会话在做（先查会话列表和大总管清单）。只有一部分有会话在做的，照常升，那一部分只列成依赖（哪个会话、哪天上线），不重复做。
2. 他否过或有意不做（例：「进垃圾箱这次不管」）。
3. 上一层归别人管（例：达人库 11-06 起归利强、智强）。
4. 上一层要业务负责人拍板，AI 负责不了。这时把上一层写成「给用户的建议」，不写成目标。

## 广度：范围写全

- **实现类**：广度指覆盖全。列出所有通道、入口、同类对象，写进「范围」。例：附件中转要对三种发信通道都生效；「添加发信邮箱」先在前端找全所有入口。手里没有清单时，派单里写「先找全，列给用户」，不自己猜。
- **方案还没定的设计、调研类**：再加一条「别的领域怎么做同一件事」。把成品的名字换成它要起的作用再问。例：不问「收件箱怎么做」，问「信入库以后和邮箱无关，谁做得最好」，得到客服工单系统。借来的做法写成「可参考」，不扩大范围。

## 深度：要处理的情况和怎么证明

- 手里有材料（原消息、排查结论、代码位置）：直接写成「要处理的情况」和验证标准。例：授权中途取消、授权失败、同一 Gmail 已被别人绑定时各显示什么；用真实 Gmail 收一封 40MB 的信，确认链接能下、信没进垃圾箱。
- 手里没有材料：在派单里写成要求，让接单的会话出方案前先回答四个问题，答案写进方案第一版：
  1. 这个领域的专家做这件事，会做哪些我们没想到的工作？
  2. 他们看哪些一手资料（原始日志、原信、客户原话），不只看整理好的报表？
  3. 用哪些具体的方法和工具？
  4. 做完以后怎样证明确实有效？
- 已知事实写明来源，并写「开工先核对，不直接当事实用」。

## 速度

按 AGENTS.md「先完成再完美」「派单按工作量估时」，不另立标准：

- 写明第一版是什么（最快能交付、能验证的版本），哪些放到第一版之后列给用户定。
- 有期限的写期限和原话。
- 接单的会话给用户报两段时间：「AI 写完、开出 PR 约 X」和「到上线约 Y」。调研类报「给出结论约 X」。

## 什么时候先问用户

默认直接写进派单就派，不先发给他确认。接单的会话在流程第 1 步自己做升维时也一样：结果写在调研单或需求清单开头，直接往下做，不单独停下等他确认目标（2026-11-20 定）。两种情况先用一两句话问：

- 升维后进了别人维护的模块（先对要改的目录跑 `git log --since=30.days --format=%an` 查维护人）；
- 工作量估计是原目标的两倍以上。手里的材料估不出来的，不问，照派，回他的那一行写「多出的工作量没估」。

问法：「原目标是 X。我想升成 Y，因为做完 X 以后 Z 还是没有。这样会多出 W。升不升？」

## 派单写法

第一行照原来的模板（大总管是「类型：飞书链接」）。紧接着写原目标那两行，或者直接目标、背后的目标那两行。原模板里「按哪个流程做」一行放在四节之前，「来源」「不要发消息给大总管」「收尾」「待开工」几行放在四节之后。四节的标题可以按内容改，括号里标维度：

```
## 目标（高度）
## 范围（广度）
## 要处理的情况（深度）
## 速度
```

哪一节没有内容就不写，不为凑齐四节填空话。派出后回用户的那一行带上：「原目标 X，升成 Y」或「没升，原因 Z」。他回「按原目标」，就把目标改回去，其余三节保留。

样板（他认可过的派单，在 `~/.claude/projects/-Users-qiansenmiao-tasks-hub/` 的会话记录里搜 `start_session` 能找到原文）：

- 11-16「发信超大附件转下载链接」：不升，完成标准按收件人能不能下载算。
- 11-16「收件箱添加发信邮箱和设置页走同一个流程」：四小节的标准写法，范围是找全所有入口。
- 11-16「Brand 和飞书企业邮箱能连到什么程度」：调研类，高度写「要解决的问题」，深度写「要回答的问题」。
- 11-17「达人回信到过我方邮箱就不在 Ordo 里丢」：整体升一层，写了原目标、第一版、第二版和他定的规则。

## 依据

- 字幕稿《AI的使用在于你的野心》（`~/Documents/Codex/2026-10-26/new-chat/outputs/AI的使用在于你的野心-结构化字幕原文.html`）：四个维度的出处。高度是反复问「做完这件事，然后呢」，逐层提高到做不好再退一层；深度是动手前的四个问题；广度是「把名词换成动词」；目标定得具体而有挑战比「尽力就好」有效。这里的用法以上面各节为准，字幕稿只作补充。
